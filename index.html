CASE STUDY 01 / DELIVERY AUTOMATION

Make each change earn its release.

How can two payment services evolve independently while keeping the checks before deployment visible and repeatable?

THE PROBLEM

Rebuilding every service for every change wastes work. Running checks without clear dependencies makes release decisions harder to trust.

THE IMPLEMENTATION

Separate transaction handling from fraud scoring. Select workflows by changed paths, run tests and source scans, then gate the container build on those jobs.

Build only what changed

Path filtering selects service workflows. The trade-off is maintaining path rules as shared dependencies grow.

Checks before packaging

Tests and source scans run in parallel; the build waits for required jobs. Image scanning happens after the Docker build.

Keep decisions explainable

Rules produce a readable risk score. This is a simulation, not a trained fraud model or evidence of real-world detection accuracy.

CASE STUDY 02 / SECURITY & RECOVERY

Tokenize the data.
Watch the service.

A FastAPI prototype exploring encrypted token storage, delivery checks, and recovery after a service failure.

THE PROBLEM

Replacing sensitive input with a token is only one part of a service. Encryption, test coverage, release controls, and runtime health need attention too.

THE IMPLEMENTATION

UUID tokens reference encrypted values in an in-memory store. The pipeline tests and scans the container before approval. A documented host-level Monit setup watches process and HTTP health.

Authenticated encryption

GCM encrypts the value and verifies an authentication tag during decryption. Key provisioning and rotation remain separate responsibilities.

Simple storage, explicit limits

An in-memory store keeps the prototype small. Tokens are lost on restart, making durable storage essential before real use.

Check more than a PID

A process can exist without responding correctly. The documented Monit configuration combines process and HTTP checks to detect both conditions.
